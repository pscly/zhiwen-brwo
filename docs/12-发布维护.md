# 12 · 发布与维护

> 这一篇是给我自己（或未来的 AI）看的：怎么发新版、出问题时怎么回滚。

## 一、发一个新版本

```bash
# 1. 改版本号（三处，必须一致）
#    core/pyproject.toml        version = "x.y.z"
#    hub/pyproject.toml         version = "x.y.z"
#    core/src/zw_core/__init__.py   __version__ = "x.y.z"
#    hub/src/zw_hub/__init__.py     __version__ = "x.y.z"

# 2. 跑测试
.venv/bin/python -m pytest tests -q

# 3. 提交
git add -A && git commit -m "x.y.z：..."

# 4. 打 tag 并推 —— 这一步会自动触发三平台构建 + 发布 Release
git tag -a vx.y.z -m "vx.y.z"
git push origin main
git push origin vx.y.z
```

推完 tag 后，去看 `Actions → 发布安装包`。约 10–20 分钟（Windows runner 最慢）。

**产物会出现在 Releases 页面**：

| 文件 | 平台 |
|---|---|
| `知纹客户端-Windows.exe` | Windows 10/11 |
| `zhiwen-client-Linux-x86_64` | Linux x86_64 |
| `zhiwen-client-macOS.zip` | macOS（含 .app） |
| `SHA256SUMS.txt` | 校验和 |

## 二、构建流程都在验什么

```
安装依赖（core + hub 都要！只装 core 会让 hub 的测试 import 失败）
  ↓
单元测试（198 项，含只在真平台才暴露的行为差异）
  ↓
PyInstaller 打包
  ↓
冒烟测试：跑 --selftest（验证依赖/控制台页面/AEAD/Argon2/机器码都在产物里）
  ↓
产物重命名 + 上传
  ↓
Release（仅 tag 触发）
```

### 冒烟测试为什么要跑 `--selftest`

打包最常见的失败是「能构建、一跑就 ModuleNotFound」：
- `core/src/zw_core/web/index.html` 是运行时读文件的，PyInstaller 的依赖分析看不到，必须显式列进 `datas`
- uvicorn 的后端（`h11_impl`、`websockets_impl`）是按名字动态加载的，也必须列进 `hiddenimports`

`--selftest` 把这些路径真的走一遍，跑不过就是打包漏了东西。

### Windows 上有个特殊的坑

GUI 子程序（`console=False`）**没有控制台**：`sys.stdout` 可能是 `None`，
`print` 出去的东西直接消失。所以：
- `--selftest` 的结果会同时写 `<配置目录>/selftest.txt`
- Windows 上还会用 `ctypes` 弹一个原生消息框（不依赖 GUI 框架）
- CI 里不会干等消息框：后台跑 + 轮询 + 超时后改看报告文件

## 三、只在真平台才暴露的问题（都已修，别再踩）

这几个都是「本地 Linux 全绿、CI 的 Windows job 挂了」：

| 现象 | 原因 | 修法 |
|---|---|---|
| `UnicodeDecodeError: charmap cp1252` | `path.read_text()` 不指定编码时用系统代码页 | 所有 `read_text/write_text` 显式 `encoding="utf-8"`；`subprocess(text=True)` 同理 |
| 配置文件权限 0o666 | `os.chmod` 在 Windows 只影响只读标志 | 走 `icacls /inheritance:r /grant:r <user>:F` |
| `os.uname` 不存在 | Windows 没有 | 用 `socket.gethostname()` |
| 时区全被拒 | Windows 没有系统时区库，`ZoneInfo` 抛异常 | 加 `tzdata` 依赖 + 代码层常见时区白名单兜底 |
| `os.kill(pid, 0)` 抛 `WinError 87` | Windows 上它是 `TerminateProcess` | 改用 `tasklist`；并兜住 `OSError` |
| `purge_expired_tokens` 返回 0 | SQLite 的 `rowcount` 对 DELETE 不是可靠契约 | 先 `COUNT` 再 `DELETE` |
| macOS 上 `timeout: command not found` | `timeout` 是 GNU coreutils | 后台跑 + `kill -0` 轮询 |
| `out/` 目录找不到 | 先 `cd dist` 再 `mkdir out`，建到了 dist 里 | 全用 `${{ github.workspace }}` 绝对路径 |

**教训**：本地全绿 ≠ 跨平台正确。发布流程里"构建前先跑测试"不是形式主义。

## 四、服务器端升级

```bash
# 在开发机
bash scripts/deploy-hub-35.sh        # 幂等，会同步代码并重建容器
```

脚本会：
1. 同步 `hub/` 到 `/opt/zhiwen-hub`
2. 保留原 `.env`（令牌、面板密码不覆盖）
3. 老 `.env` 缺的配置项自动补上（不改已有值）
4. 重建容器并**轮询到就绪**（失败时打出容器日志）

> 坑：脚本必须把 `docker-compose.yml` 一起同步。只同步代码不同步 compose 会导致
> 「改了 .env 但容器行为没变」—— 因为 compose 里的环境变量默认值还是旧的。

### 升级后检查

```bash
curl -s http://192.168.3.5:8700/healthz | jq .data.version     # 版本对不对
curl -s http://192.168.3.5:8700/v1/enroll-info | jq .data       # 对接码策略
curl -s -o /dev/null -w "%{http_code}\n" http://192.168.3.5:8700/   # 面板可访问
```

## 五、回滚

```bash
# 代码回滚
git revert <commit> && git push origin main
bash scripts/deploy-hub-35.sh

# 或者回到上一个 tag
git checkout v0.2.0 -- . && bash scripts/deploy-hub-35.sh
```

**数据不会丢**：快照在 `/srv/zw-hub/data`，设备表在 `/srv/zw-hub/data/devices.db`，
升级不动它们。真要重来，把这两个目录备份/移走后重启即可。

```bash
# 备份（建议加进服务器 crontab）
ssh 192.168.3.5 'sudo tar czf /backup/zw-hub-$(date +%F).tgz -C /srv/zw-hub data'
```

## 六、撤销一个设备

| 目的 | 做法 |
|---|---|
| 让某台机器连不上 | 面板「踢下线」（可恢复，重连不能自愈） |
| 彻底清掉它的记录 | 面板「删除」（它下次启动会作为新设备回来） |
| 连它本机配置也清掉 | 在**那台机器**上删 `%LOCALAPPDATA%\zhiwen-client\client.json` |

删本地配置 = 变成一台"新机器"。这是绕过踢下线的唯一方式，
但服务器上会多一条新设备记录 —— 反而更容易被发现。
