# 07 · 排错手册

> 按"现象"查，不用按模块。
> 第一步永远是：`zw doctor`，第二步是看日志（位置见 [08](08-运维与日志.md)）。

---

## 一、启动相关

### `ENGINE_NOT_FOUND` — 找不到浏览器内核

```
没有找到 Chromium 内核。三种解决办法任选其一：
  1) 把内核解压到 <数据目录>/engines/ 下
  2) 设置环境变量 ZW_CHROME_BIN 指向 chrome 可执行文件
  3) 安装系统版 Chromium / Chrome
```

```bash
# 确认程序看到了什么
zw doctor | grep -A3 浏览器内核
# 手动验证
/path/to/chrome --version
```

### `ENGINE_EXITED` — 浏览器起来就退

看 `<环境目录>/browser.log`。最常见的三种：

| 日志里看到 | 原因 | 解决 |
|---|---|---|
| `Missing X server or $DISPLAY` | Linux 无图形界面 | 程序会自动加 `--headless=new`；如果不会，检查 `echo $DISPLAY` 与你是否手动覆盖了 `ZW_CHROME_EXTRA_ARGS` |
| `Running as root without --no-sandbox` | root 用户 | 程序已自动加；若仍报，手动 `ZW_CHROME_EXTRA_ARGS="--no-sandbox"` |
| `cannot open shared object file` | 缺系统库 | 装 `libnss3 libatk-bridge2.0-0 libgtk-3-0` 等（Debian 系：`apt install chromium` 会一起装） |

### `LAUNCH_TIMEOUT` — 45 秒没起来

```bash
# 1. 端口是不是被占
ss -lntp | grep 21001

# 2. 手动跑一次看输出
/path/to/chrome --user-data-dir=/tmp/t1 --remote-debugging-port=21999 \
  --no-first-run --no-sandbox about:blank
curl -s http://127.0.0.1:21999/json/version

# 3. 杀软/EDR 拦截（Windows 上常见）
```

### 启动成功但 `cdp.gateway_ws_url` 为空

说明服务端没能自己解析一次发现接口。看返回里的 `hint` 字段，通常是：
- 浏览器刚起来还没就绪 → 重新 `GET /profiles/{id}/cdp`
- 网关路由没登记 → 重启 core（会自动重建）

## 二、网关 / 连接相关

### Playwright 报 `connect ECONNREFUSED 127.0.0.1:21001`

**这是最典型的症状**：说明你拿到的是**没被重写**的地址，连到本机去了。

```bash
# 检查发现接口返回的是不是网关地址
curl -s "http://<core>:8730/cdp/<id>/json/version?token=..." | jq -r .webSocketDebuggerUrl
# 期望：ws://<core>:8730/cdp/<id>/devtools/browser/<GUID>?token=...
# 如果看到 127.0.0.1:21001 就是重写没生效（不该发生，报 bug）
```

### `401 UNAUTHENTICATED`（CDP 通道）

令牌过期（默认 15 分钟）。重新取：

```bash
zw profile cdp <环境>
```

### `websocket: bad handshake` / 立即断开

- 新版 Chromium 需要 `--remote-allow-origins=*`，知纹已自动加；
  如果你是手动跑的浏览器，要自己加。
- 检查是不是同一环境第 9 个连接（`ZW_CDP_MAX_CONN` 默认 8）。

### 网关报 `ROUTE_NOT_FOUND`（503）

环境没在跑，或者 core 重启后路由没恢复。

```bash
curl -s -H "Authorization: Bearer $T" http://127.0.0.1:8730/api/v1/events | jq .data.gateway_routes
# 重启 core 会自动重建；运行中的浏览器不受影响
```

## 三、cookie 相关

### `409 STATE_CONFLICT` — 环境没运行

**这是设计，不是 bug。** 停止状态下磁盘上的 `Cookies` 是 OS 密钥加密的密文，读出来没用。

```bash
zw profile start <环境>
# 或让接口代你启动
curl -X PUT .../cookies -d '{"cookies":[...],"start_if_needed":true}'
```

### 写进去的 cookie 一个都没成功

看返回里的 `failures` 数组，常见原因：

| failures 里写着 | 原因 |
|---|---|
| `字段不全` | 缺 `name` 或 `domain` |
| `... sameSite` 相关 | `sameSite` 传了空串。只接受 `Strict`/`Lax`/`None` |
| 大量 `expired` | cookie 本来就过期了，正常 |

### 导入了 cookie 但站点还是未登录

三个常见原因：

1. **漏了 `partitionKey`**：CHIPS 类第三方 cookie 没带分区键会失效。
2. **域不匹配**：`.example.com` 和 `example.com` 是两个不同作用域。
3. **站点用的是 localStorage 而不是 cookie**：用 `zw profile` 的 storage 接口补齐。

## 四、同步相关

### `KEY_FINGERPRINT_MISMATCH`（412）

**不要重试。** 三条路：

```bash
# 1. 确认你的主密码
echo -n "$ZW_SYNC_PASSWORD" | wc -c     # 至少 12

# 2. 确认远端是用哪个口令推的
zw sync diff <环境>      # 会显示 remote_pw_fp 与 local_pw_fp

# 3. 确定要以远端为准（会覆盖本地，先备份）
curl -X POST .../sync/<id>/pull -d '{"password":"正确口令","force":true}'
```

### `REVISION_EXISTS`（409）

别的机器已经推过这个版本号。

```bash
zw sync diff <环境>       # 看远端到几了
zw sync pull <环境>       # 对齐
zw sync push <环境>       # 再推
```

### `PROFILE_BUSY`（409）

有人持有租约。

```bash
# 本地租约（本机死进程）
zw profile unlock <环境>

# hub 租约（另一台机器）
curl -s -H "Authorization: Bearer $HUB_TOKEN" http://192.168.3.5:8700/v1/leases/<id>
# 等 TTL（默认 90 秒）过期，或让对方正常释放
```

### `HUB_UNREACHABLE`

```bash
curl -s http://192.168.3.5:8700/healthz
ssh 192.168.3.5 'sudo docker ps --filter name=zw-hub; sudo docker logs zw-hub --tail 30'
```

### `NO_REMOTE`

hub 上没有这个环境，先在源机 push：

```bash
zw sync push <环境>
```

### 同步后掉登录

按顺序排查：

1. `zw sync diff <环境>` 看 revision 对不对
2. 检查包里有没有 `Default/Cookies`（不该有）
3. 看 pull 返回的 `cookie_report.ok` / `fail`
4. 回滚：

```bash
ls <环境目录>/udd.bak.*          # 找到上一个
# 停环境 → 把 udd 改名 → 把 udd.bak.<rev> 改名成 udd → 启动
```

## 五、控制台 / 令牌

### 控制台一直弹"需要访问令牌"

浏览器 localStorage 里存的是旧令牌。

```js
// 在控制台按 F12
localStorage.removeItem('zw_token');
location.reload();
```

### `ZW_HOST=0.0.0.0` 启动被拒

```
ZW_HOST 不是回环地址时必须设置 ZW_ADMIN_TOKEN……
```

这是**故意的**：不加令牌等于把浏览器裸奔在局域网上。
真想在无令牌情况下开放，显式设 `ZW_FORCE_TOKEN_ON_PUBLIC=false`（不推荐）。

## 六、Windows 专属

| 现象 | 原因 | 解决 |
|---|---|---|
| 双击 `启动.cmd` 闪一下就没了 | 没装 uv / Python | 按 [快速开始](01-快速开始.md) 先装环境 |
| 杀软报毒删掉 chrome.exe | fingerprint-chromium 是未签名构建 | 把引擎目录加白名单 |
| 端口被 Hyper-V 占用 | Windows 会预留端口段 | `netsh int ipv4 show excludedportrange protocol=tcp`；把 `ZW_PORT_POOL` 换到闲段 |
| 中文路径下启动失败 | 部分 Chromium 构建对非 ASCII 路径敏感 | 把数据目录换到纯英文路径（`ZW_ROOT`） |
| 服务重启后浏览器没了 | core 退出时不会杀浏览器 | 这是有意的（控制面重启不影响浏览器）；重新 `zw profile start` 会检测到已在跑 |

## 七、给 AI 的排错指令

把这段直接喂给 agent：

```
知纹出问题了，按这个顺序查，不要跳步：
1. 调 zw_doctor，把每个 ❌ 的详情贴出来
2. 调 zw_list_profiles，找出 state 不是 running/stopped 的
3. 对这些环境调 zw_read_logs（tail=100），重点看 browser.log 的最后 20 行
4. 如果涉及同步，调 zw_sync_diff 看 revision 与 pw_fp
5. 给出结论：是环境问题、内核问题、还是同步密码问题
6. 不要自己执行 reset-fingerprint / delete，先问我
```

## 八、日志里该找什么

日志是 JSON 行，直接 jq：

```bash
# 只看错误
jq -c 'select(.level=="ERROR")' <数据根>/logs/zhiwen.log | tail -20

# 某个环境的全部事件
jq -c 'select(.profile_name=="小红一号")' <数据根>/logs/zhiwen.log

# 审计里看谁动过
curl -s -H "Authorization: Bearer $T" \
  "http://127.0.0.1:8730/api/v1/audit?limit=50" | jq '.data.items[] | [.ts,.action,.result]'
```
