# 16 · 代理与扩展包

> 两件配套的事：**代理**（怎么导入、怎么测、怎么改、带认证怎么跑通）
> 与 **扩展包**（把某个浏览器里的插件连数据一起打包，新建时默认带上）。

---

## 一、代理：为什么带密码的代理需要"本地中继"

### 问题

Chromium 的 `--proxy-server` **不支持用户名密码**。写成
`http://user:pass@host:port` 时它会把整串当主机名，结果是连不上，
而且报错完全看不出原因。

更麻烦的是：**Chrome 137 之后已经忽略 `--load-extension`**。
（实测：Chrome 149 上用一个带 content_script 的扩展，页面里取不到标记 → 没被加载。）
所以原来"生成一个认证扩展去应答 `onAuthRequired`"的方案在新内核上会**静默失效**。

### 解法：本机中继

```
Chrome --proxy-server=http://127.0.0.1:<relay_port>   ← 无认证，引擎原生支持
        │
        ▼
知纹本地中继（只绑 127.0.0.1）
        │  在这里补 Proxy-Authorization，或做 SOCKS5 用户名密码握手
        ▼
上游代理 socks5://user:pass@host:port  /  http://user:pass@host:port
```

好处：**引擎无关**（不依赖扩展、不依赖 Chrome 版本）、可观测（中继自己知道连没连上）、
可测（单测里起假上游就能验完整握手）。

设计要点：

- 只绑 `127.0.0.1`，绝不 `0.0.0.0`（否则等于给全网开代理）
- SOCKS5 CONNECT 把目标域名交给上游解析。`socks5h://` 可直接导入，保存时统一为 `socks5://`。
- 配置 SOCKS5 后，知纹启动 Chromium 时限制本地解析。浏览器直连代理时可以解析代理主机名。经过中继时，浏览器只需连接回环地址。如果中继的入口代理配置为域名，中继仍需解析该域名。此保护针对上述浏览器代理链路，系统其他程序和浏览器其他网络机制需要分别验证。
- 上游连不上时回 `502` 并带原因；静默断开在浏览器里表现为"一直转圈"，最难查
- 日志不含密码

开关：`ZW_PROXY_RELAY`（默认 `true`）。设为 `false` 会退回旧的扩展方案（老内核可用）。

## 二、代理库：导入 / 测试 / 换代理

### 批量导入

一行一个，支持这些写法：

| 写法 | 说明 |
|---|---|
| `socks5://user:pass@1.2.3.4:20000` | 最常用 |
| `http://user:pass@5.6.7.8:8080` | HTTP 代理 |
| `9.9.9.9:1080:user:pass` | 代理商的常见格式 |
| `user:pass@1.2.3.4:1080` | 省略协议（默认 http） |
| `10.0.0.1:3128` | 无认证 |
| `… # 香港住宅01` | 行尾备注会成为 label |

密码里的 `@`、`/`、`#` 要写成 `%40`、`%2F`、`%23`（或直接写原文，因为
"host:port:user:pass" 这种格式会按最后一个冒号切）。

**分号不会自动切分；逗号只有在写链时才切**（见第三节）——代理串里可能就有这些字符，
所以逗号只当兜底分隔符：单跳解析成功了就绝不切。要写链请优先用 `|` 或 `>>`。

```bash
curl -X POST http://127.0.0.1:8730/api/v1/proxies/import \
  -H 'Content-Type: application/json' \
  -d '{"text":"socks5://u:p@1.2.3.4:20000\n10.0.0.1:3128  # 直连"}'
```

返回里 `imported / skipped / ignored / failed` 分开计数，失败行带原因，不影响其它行。
**响应里不会出现密码。**

### 测试出口

```bash
# 测一条临时串（不用先入库）
curl -X POST http://127.0.0.1:8730/api/v1/proxies/test \
  -H 'Content-Type: application/json' -d '{"raw":"socks5://u:p@1.2.3.4:20000"}'

# 批量测库里的
curl -X POST http://127.0.0.1:8730/api/v1/proxies/test-many \
  -H 'Content-Type: application/json' -d '{"ids":[1,2,3]}'
```

socks5 的检测依赖 `httpx[socks]`（已写进 core 依赖）。

### 创建之后换代理

```bash
# 从代理库选
curl -X PUT http://127.0.0.1:8730/api/v1/profiles/<ref>/proxy \
  -H 'Content-Type: application/json' -d '{"proxy_id":3}'

# 或者直接给串（会自动入库）
curl -X PUT http://127.0.0.1:8730/api/v1/profiles/<ref>/proxy \
  -H 'Content-Type: application/json' -d '{"raw":"socks5://u:p@1.2.3.4:20000"}'

# 清除
curl -X PUT http://127.0.0.1:8730/api/v1/profiles/<ref>/proxy \
  -H 'Content-Type: application/json' -d '{}'
```

**运行中的环境不能热改**（Chromium 的 proxy 是启动期参数），返回
`restart_required: true`，先 stop 再 start。

界面上：客户端 → 环境行「代理」按钮；或 Web 控制台 → 代理页「批量导入」。

## 三、链式代理（前置 → 落地）

### 为什么需要

有些落地代理**直连永远不通**，只能经某条前置访问：

- 机场/中转提供的 SOCKS5 落地，只认前置那条线路的出口 IP；
- 代理商给的"住宅落地"绑了白名单，你的家宽 IP 不在里面，但机场可以；
- 落地在海外机房之间做跳板，机房侧只放行特定上游。

这种代理单独填进知纹，症状是**超时**（不是认证失败），而你在别的软件里填
"前置 + 落地"是通的 —— 因为那个软件会串两跳，而知纹（以及 Chromium）只会用一层。

### 怎么写

用 `|` 把两段连起来：**左边是前置，右边是落地**。

```
http://127.0.0.1:21080 | socks5://cf1b481103:51ec63a321@66.80.12.66:20000
```

顺手写的 `,` 和 `>>` 也认（同一个意思）：

```
http://127.0.0.1:21080, socks5://user:pass@66.80.12.66:20000
http://127.0.0.1:21080 >> socks5://user:pass@66.80.12.66:20000
```

两段都支持"单跳"里的所有写法，所以前置可以写成代理商那种四段简写：

```
127.0.0.1:21080:hopuser:hoppass | socks5://land:landpw@66.80.12.66:20000
```

导入时整行会作为一个代理条目入库，`hop` 字段单独存前置（含它自己的凭据）。
列表里显示成 `前置 → 落地`，两边的密码都是 `***`。

> **`|` 与 `>>` 是无条件的分隔符；`,` 是兜底。**
> 因为凭据里有真的可能带逗号（`http://u:pa,ss@h:8080`）。所以解析顺序是：
> 先认显式链 → 再按单跳解析 → 单跳失败才按逗号切。
> 换句话说：**密码里有逗号时别用逗号写链**，用 `|`。

### 只支持两跳

前置 + 落地，就两跳。写成三段（`a|b|c`）会明确报错：

```
PROXY_CHAIN_TOO_LONG：只支持两跳（前置 | 落地），这行有 3 段
```

不做任意长度链的理由：每多一跳多一层握手、多一层超时叠加、多一处"到底哪跳坏了"
的模糊地带，收益远小于排查成本。三跳及以上的诉求通常意味着"该换个落地"。

### 落地侧 DNS 依然成立

链式下 SOCKS5 的 `CONNECT` 仍然发**域名**（`ATYP=0x03`），由**落地**去解析。
前置只是把字节搬到落地，不参与解析 —— 否则 DNS 会落在前置那一侧，
等于绕过落地所在地区的解析结果，指纹浏览器最在意的 DNS 一致性就没了。
`tests/test_proxy_chain.py` 里对这一点有断言（落地收到的目标是域名而不是 IP）。

### 内部是怎么做的

`--proxy-server` 只能表达**一层**代理，所以链式**一律**走本机中继（哪怕两跳都不需要认证）：

```
Chrome --proxy-server=http://127.0.0.1:<relay_port>     ← 无认证
        │
        ▼
知纹本地中继
        │  ① CONNECT 落地:port  (+ 前置自己的 Proxy-Authorization)
        ▼
   前置代理（http 或 socks5，可带认证）
        │  ② 在这条隧道里对落地做 SOCKS5 握手 / 再发一次 CONNECT
        ▼
   落地代理（http 或 socks5，可带认证）
        │  ③ 裸字节流：浏览器 ↔ 目标
        ▼
      目标站点
```

中继里"连上某个代理"（`_connect_proxy`）与"在连接上完成握手"（`_handshake`）
是分开的两个函数，`_open_tunnel(spec, host, port)` 把它们串起来；链式就是
"先用前置开隧道，再在这条隧道上对落地握一次手"。这也是这次重构的核心：
旧实现把连接和握手焊死在 `_socks5_connect` 里，第二条连接根本没法复用。

### 排错：错在哪一跳

两跳的故障症状一模一样（超时/认证失败），所以错误信息里**一定带角色**：

| 你看到的 | 含义 | 该改什么 |
|---|---|---|
| `前置代理：连不上上游代理 127.0.0.1:21080（ConnectionRefused…）` | 前置本身没起来/端口错 | 本机代理软件、前置地址 |
| `前置代理：上游代理拒绝认证（407）` | 前置的账号密码错 | 前置凭据 |
| `落地代理：上游 SOCKS5 用户名密码认证失败` | 落地凭据错 | 落地凭据 |
| `落地代理：连不上上游代理 66.80.12.66:20000` | 前置通了，但它到不了落地 | 落地的地址/白名单 |

中继的 `stats()` 里也有 `chain`（`前置|落地`，不含凭据）、`is_chain` 与 `last_error`，
`zw proxy status` / 控制台代理页能看到。

> **已知边界（0.7.x）**：链式条目请**从代理库导入**（或 `PUT /profiles/<ref>/proxy`
> 带 `raw` 自动入库）。直接把带 `|` 的串写进环境的 `proxy` 字段时，入库前会被脱敏成
> 只留落地地址，前置就丢了 —— 那种情况会退化成"直连落地"（症状：一直超时）。
> 修这个要走 `manager.proxy_spec_for()` 的字段，不在本次改动范围内。

### 检测出口

`POST /api/v1/proxies/test` 对链式条目也照常可用：中继会临时起一个（不进端口池），
经两跳去取出口 IP，探完立刻关掉。失败时错误信息里会附上中继的具体原因
（例如"前置 407"），而不是一句笼统的"连接被重置"。

## 四、扩展包

### 是什么

一个包 = **扩展代码** + **该扩展的本地数据**（`Local Extension Settings/<id>`）。

用途就是你说的："把 RXYCDP 浏览器里的插件及其数据一起打包，以后创建浏览器默认带上"。

### 不搬什么（刻意的）

| 不搬 | 原因 |
|---|---|
| `Local Storage/leveldb` | 一个库混着所有源的键值，挑不出"只属于这个扩展"的边界，硬解析等于赌键编码 |
| `Sync Extension Settings/` | 云端权威，搬过去会被云端覆盖 |

### 用法

```bash
# 从某个已有环境导出（这就是 RXYCDP 那个场景）
curl -X POST http://127.0.0.1:8730/api/v1/packs/import \
  -H 'Content-Type: application/json' \
  -d '{"from_profile":"<环境ref>","name":"RXYCDP 全套"}'

# 设为新建环境默认带上
curl -X POST http://127.0.0.1:8730/api/v1/packs/<pack_id>/default \
  -H 'Content-Type: application/json' -d '{"enabled":true}'

# 应用到某个已有环境
curl -X POST http://127.0.0.1:8730/api/v1/profiles/<ref>/packs/apply \
  -H 'Content-Type: application/json' -d '{"pack_ids":["<pack_id>"]}'
```

界面上有两条导入路径：

| 你的情况 | 用哪个 | 怎么填 |
|---|---|---|
| 插件装在**知纹自己的环境**里 | 「从环境导入」 | 选那个环境 |
| 插件装在**别的浏览器**里（Roxy / RXYCDP / 官方 Chrome） | 「从 Chrome 目录导入」 | 填那个浏览器的用户数据目录，例如 `%LOCALAPPDATA%\Google\Chrome\User Data`（也可以直接给里面的 `Default`） |

「从 Chrome 目录导入」是他们这类场景的关键：RXYCDP/Roxy 不是知纹启动的，
它的扩展不在知纹的 profiles 目录里，而在标准 Chrome 的
`User Data/Default/Extensions/<id>/<ver>/`，数据在
`User Data/Default/Local Extension Settings/<id>/`。给个路径就能一起打包。

接口对应：
```bash
POST /api/v1/packs/import
{"from_chrome": "C:/Users/你/AppData/Local/Google/Chrome/User Data", "name": "RXYCDP 全套"}
```

> **`path` 也认浏览器目录**（0.8.5 起）：如果你把路径填进 `path` 而不是 `from_chrome`，
> 系统会嗅出这是浏览器的 `User Data`（或里面的 `Default`），**自动按带数据的方式导入**。
> 以前这种情况会"导入成功但数据丢失"——扩展带上了、登录态没带上，且不报错。
> 现在两种填法都会带上 `Local Extension Settings`。

开关：`ZW_DEFAULT_PACKS`（默认 `true`）控制"新建环境是否自动带上所有默认包"。

> **跨机**：包默认存在**本机**（`<数据目录>/packs/`）。0.8.14 起可以把包上传到
> **控制台**（主控台「扩展包」页），别的机器用「从控制台拉取」取回本机 ——
> 这才是"一次打包、多机使用"的正路。也可以直接把 `packs/` 目录拷过去。

> **还有一个前提**：能否加载扩展取决于内核。Chrome 137+ 忽略
> `--load-extension`（见第一节），这类内核上扩展包不会被加载。
> 代理认证不依赖扩展（走本地中继），所以代理不受影响。

## 四点五、扩展 ID 与「升级后登录态丢失」

未打包扩展（`--load-extension` 加载的那种）**没有 manifest 公钥**，Chromium 用
**加载路径**推导它的 ID：`SHA-256(路径)` 取前 32 个 hex，再映射成 a–p 的字母。

后果很直接：扩展目录名里带版本号（`bitwarden-password-manager-2026.10.2`）时，
扩展一升级 → 目录变 → ID 变 → 浏览器去一个**全新的空目录**
`Default/Local Extension Settings/<新ID>/` 找数据。用户看到的是
「Bitwarden 又要重新登录」「脚本猫的脚本没了」，而数据其实还躺在旧 ID 目录里。

### 现在的做法

- 扩展库目录**固定成 `<slug>`，不带版本号**（`<数据目录>/extensions/<slug>/`）。
  升级时把新代码完整复制到 `<slug>.staging`，再 rename 覆盖，路径不变 → **ID 恒定**。
- 存储数据仍然按 ID 命名（这是 Chromium 的规则，改不了），但因为 ID 不再漂移，
  一次登录长期有效。

### 历史上已经漂过的环境怎么修

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{}' http://127.0.0.1:8730/api/v1/maintenance/extensions/repair
```

- 会把每个环境里「旧版本目录推导出来的 ID」目录，**复制**到当前 ID 目录；
- 目标目录已经有数据时**不覆盖**（宁可留着新的，也不拿旧的盖掉）；
- 旧目录改名成 `<旧ID>.migrated` **保留**，确认没问题再手工删；
- 只处理确定的同一个扩展，不跨扩展搬运，也不动扩展代码目录。

> 先停环境再跑。运行中的浏览器占着 leveldb，迁移会失败（接口会如实报错，
> 不会假装成功）。

## 五、浏览器启动时默认打开什么

用户要的语义是：**先恢复上次关闭时的网址，再追加一个检测页**。

| 配置 | 默认 | 作用 |
|---|---|---|
| `ZW_RESTORE_TABS` | `true` | 启动时恢复上次的标签页 |
| `ZW_OPEN_DETECT_ON_START` | `true` | 追加检测页 |
| `ZW_DETECT_URLS` | 见下 | 检测页列表（逗号分隔） |

怎么"记住"上次的标签：**关浏览器之前**用 CDP `Target.getTargets` 抓一次
（浏览器级命令，不 attach、不改状态），写回 `start_urls`。
不去解析 Chromium 的 `Sessions/*.bin` —— 那是二进制私有格式，逆它等于给自己埋雷。

默认检测页（都实测过能打开且真的显示数据）：

| 网址 | 看什么 |
|---|---|
| `https://browserleaks.com/ip` | 出口 IP + WebRTC 泄漏 |
| `https://ip123.in/` | 中文界面的 IP 纯净度（欺诈评分/代理特征/黑名单/是否原生 IP） |
| `https://abrahamjuliot.github.io/creepjs/` | 综合指纹（FP ID、fuzzy hash） |

被剔除的（实测不可用）：`ping0.cc`（Cloudflare 验证墙）、
`scamalytics.com/ip`（是查询表单，不自动显示自己）、`ip.cn`（探到 127.0.0.1）、
`whoer.net`（只有"请稍候…"）。

调用方显式传了 `urls` 时**不追加**检测页（脚本/AI 想开指定页面就该照做）。

### 四、代理串的格式校验（0.7.5）

填错代理以前是**静默失败**：串被原样收下、存进库、显示在界面上，然后浏览器起来没有网络，
任何地方都没有提示。用户真实踩过这一条：

```
socks5://cf1b481103:51ec63a321@66.80.12 0.66:20000
                                    ↑   ↑
                                 空格   IP 五段
```

现在解析时就会拒掉，并说清错在哪：

| 情况 | 错误码 | 提示 |
|---|---|---|
| 主机名里有空格/制表符 | `PROXY_INVALID_HOST` | 会点明"是不是把 `66.80.12.66` 写成了 `66.80.12 0.66`" |
| 形似 IP 但不是四段 | `PROXY_INVALID_HOST` | `IP 应该是 4 段（a.b.c.d），现在有 5 段` |
| 某段不在 0-255 | `PROXY_INVALID_HOST` | `IP 段不合法：「999」` |
| 方括号里不是合法 IPv6 | `PROXY_INVALID_HOST` | `方括号里必须是合法 IPv6，例如 [::1]` |
| 端口不是数字 / 越界 | `PROXY_INVALID` / `PROXY_INVALID_PORT` | — |

三条入口都拦：**导入时**（`import_batch` 的 `failed` 里给出脱敏原因）、
**绑定到环境时**（`assign_to_profile` 返回 `ok=false` + 错误码）、
**启动时**（`mgr.start` 抛 `PROXY_INVALID_HOST`，而不是起一个没网的浏览器）。

主控台也看得见：代理列显示红色的「代理无效」，点开是具体原因和改法 ——
不用等用户去点"启动"才发现。错误信息里的密码永远是 `***`。

IPv6 字面量（`socks5://[::1]:1080`）是支持的。

### 五、能不能加载扩展，得**实测**（正式版 Chrome 不行，ungoogled 行）

这条直接影响"创建浏览器时默认带上插件"的效果，所以放在最前面。

#### 实测矩阵（2026-11-17）

| 内核 | 版本 | `--load-extension` | 判据 |
|---|---|---|---|
| `/usr/bin/google-chrome`（正式版） | 149.0.7827.53 | ❌ 不加载 | 内容脚本没执行 |
| ungoogled-chromium | 150.0.7871.186 | ✅ **加载** | 内容脚本执行、`document.title` 被改 |
| playwright chromium | — | 调试端口起不来，未判定 | — |

**结论：官方 Chrome 从 137 起关掉了这个能力，但 ungoogled-chromium 仍然保留。**
所以要"插件真的出现在浏览器里"，**换内核就行**（项目本来就支持自己指定引擎）。

#### 两个踩过的坑（都是判据选错，不是功能坏）

1. **不能用版本号判断。** 最初按"版本 ≥137 就不支持"来判，结果 ungoogled 150
   明明可以却被误判成不行。版本相同、结论相反。
2. **不能用 `/json/list` 里有没有 `chrome-extension://` 目标判断。** ungoogled 上
   这个目标**不出现**（MV3 的 service worker 不一定被列出），但扩展确实生效了。
   唯一可靠的信号是**内容脚本有没有在页面里留下痕迹**。

#### 现在的做法：跑一次探针（约 2～11 秒，结果缓存）

`services/extprobe.py`：

1. 造一个一次性扩展：manifest v3 + 一条 content_script，只做
   `document.title = "ZW-EXT-PROBE-OK"`；
2. 本地起一个只返回空页面的 HTTP 服务（content_script 不匹配
   `about:blank`/`data:`，必须给它一个真的 http 页面）；
3. 无头启动内核，带 `--load-extension=<探针>` 和调试端口；
4. CDP 导航到那个页面，读 `document.title`；
5. 看到标记 = 会加载。

结果按（内核路径 + 大小 + mtime）缓存在数据目录的 `extension-probe.json`：
同一个内核只探一次，换了版本自动重探。探测跑不起来（文件不存在/起不来）时
**按"不能加载"告警**，绝不静默放行。

#### 接口会明确告诉调用方

```json
{"extensions_active": true,  "extensions_note": ""}
{"extensions_active": false,
 "extensions_note": "实测：这个内核忽略 --load-extension（内容脚本没有执行），扩展的代码与数据会带进环境，但浏览器不会加载它"}
```

代码（`extensions/<key>/`）、数据（`Local Extension Settings/<id>/`）、
`profiles.extensions` 的 slug 无论哪种情况都完整搬运 —— 换成支持的内核后立刻生效。

#### 三条可选的落地路线

1. **换 ungoogled / fingerprint 内核**（推荐，实测有效，不改一行代码：
   客户端设置里或 `ZW_CHROME_BIN` 指过去即可）
2. **CRX + 企业策略强制安装**（`ExtensionInstallForcelist` + update manifest）——
   正式版 Chrome 上也确定可行，代价是要给扩展签名、Windows 上写 HKCU 策略
3. **手工装一次**：`chrome://extensions` 开开发者模式拖进去，数据交给包机制维护

### 六、代理库在服务器与用户机之间同步（0.7.14）

用户要求：

> 代理可以在服务器里面进行添加管控，也可以在用户机上添加管控，都是一样的…
> 用户机上添加过的代理，都会自动同步到服务器里面，也可以在服务器里面删除，或者隐藏

所以它是一份**共享库**，不是单向下发。

#### 数据流

| 方向 | 触发时机 | 行为 |
|---|---|---|
| 上行（用户机 → 服务器） | 导入代理 / 新增并绑定环境之后，**后台线程**自动推 | 按 `scheme+host+port+username+hop` 去重，只 upsert，不删 |
| 下行（服务器 → 用户机） | core 启动时自动；也可 `POST /api/v1/proxies/sync` 手动触发 | 补进本机没有的，更新标签；**不覆盖**本机密码 |
| 删除 | 服务器上删 | 该条从库中移除；用户机下次拉取时不再出现 |
| 隐藏 | 服务器上隐藏 | 默认列表与设备拉取里都不出现；**不删**、不影响已在用它的环境 |

两个方向都**绝不阻断本地操作**：服务器连不上时同步只记日志并返回 `ok:false`，
导入/启动照常。

#### 接口

面板侧（要登录）：

```
GET    /v1/proxies                      列出（默认不含隐藏项；?include_hidden=1 全要）
POST   /v1/proxies                      新增或更新（password 传空 = 不改已有密码）
POST   /v1/proxies/{id}/hide            隐藏 / 取消隐藏（{"hidden": true|false}）
DELETE /v1/proxies/{id}                 删除
```

设备侧（要设备身份，被踢/被拒绝的设备 403）：

```
POST /v1/devices/proxies                上报本机代理库（客户端自动调）
GET  /v1/devices/proxies?with_secrets=1 拉取服务器库（含密码，本机才能真的用）
```

客户端本地：

```
POST /api/v1/proxies/sync               立刻做一次往返同步
GET  /api/v1/proxies/sync               看上次同步结果（时间/上下行统计/错误）
```

#### 密码怎么存（必须交代）

"服务器加、用户机用"就要求密码能落到服务器上。为了不 naked 存储：

- 用 `panel_secret`（已持久化在 `<data>/panel-secret`，`0600`）经 **HKDF** 派生出
  独立密钥（与会话签名在密码学上分开），再做 **XSalsa20-Poly1305** 认证加密
- 库里只有 `password_enc`，**明文不落库**（有测试直接扫 sqlite 文件）
- 列表接口永远只给 `has_password`，明文只走 `/v1/devices/proxies`（设备专用）
- 密钥变了会明确报 `PROXY_SECRET_UNREADABLE`，**不会**静默当成"没有密码"

#### 一个坑

`scheme` 字段要能接受 `http://` —— 面板上这么填最自然，不做规范化会拼出
`http://://svr@host:port`。`proxies.norm_scheme()` 统一处理。

### 七、输入商店链接直接装扩展（0.7.17）

三种入口，都在客户端侧（服务器常常没有外网/没有用户的代理，客户端才有）：

```bash
# ① 粘商店链接（也接受 32 位 ID）
POST /api/v1/extensions/install
{"url": "https://chromewebstore.google.com/detail/cookiemanager-cookie-edit/hdhngoamekjhmnpenphenpaiindoinpo?hl=zh-CN"}

# ② 手动拖进来一个 .crx 或 .zip
POST /api/v1/extensions/install
{"path": "C:/Users/你/Downloads/cookiemanager.crx"}

# ③ 查已装扩展有没有新版
GET /api/v1/extensions/updates
```

接受的链接形态（都有测试）：带/不带 slug、`?hl=zh-CN`、`?id=<id>`、裸 32 位 ID。

**CRX 结构**（实测 cookiemanager：164717 字节）：

```
0    'Cr24' | 4  version=3 | 8  header_len=1310 | 12 header | 1322 ZIP(PK\x03\x04)
```

切掉 `12 + header_len` 之前的部分就是标准 ZIP。CRX2 也支持。
商店限流会返回 HTML 页面 —— 报错会直接说"多半是商店限流或需要代理"。

**装完自动建包**（0.7.19 起，默认开）：只把代码放进
`<数据目录>/extensions/<slug>-<version>/` 是**没用的** —— 没有任何环境会引用它
（`create_profile` 只按"默认包"挂扩展）。所以 `install()` 装完顺手调
`packs.import_pack()` 建包，`as_default=true` 再标成"新建环境自动带上"：

```bash
POST /api/v1/extensions/install {"url": "...", "as_default": true}
```

建包失败**不影响安装**（代码已落盘，返回 `pack_error` 让人手动建）。

**整条链路的终点判据**（有集成测试盯着，需要支持 `--load-extension` 的内核）：

```
装 CRX → 建包 → 设默认 → 新建环境（extensions 含 slug）→ 启动
      → 命令行带 --load-extension=<库路径> → 页面里内容脚本留下标记
```

实测（ungoogled 内核）：`data-store-installed = 'YES'`。

**更新**：装完在目录里写 `.zw-ext-id`；`extensions/updates` 拿它回商店比对
（当前版本从目录名 `<slug>-<version>` 读）。手工导入的包没有 ID 标记 → 跳过，
**不瞎猜 ID 去下载别人的扩展**。新版本装到新目录，旧目录保留，
正在用旧版的环境不会被突然换掉。


## 建环境时不要默认插件包

默认扩展包（`is_default=1`）会在**新建环境时自动带上**。想建一个干净的环境：

```bash
curl -X POST "$CORE/api/v1/profiles" -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"name":"干净环境","with_default_packs":false}'
```

GUI/控制台里新建时也有对应勾选。这条开关的用途：临时环境、做指纹对照、
排查"是不是某个插件导致的问题"。


## 附：启动时打开的检测页

浏览器启动后默认会打开这几页（在恢复上次标签之后追加，**不会重复**）：

| 用途 | 地址 |
|---|---|
| 出口 IP | `https://browserleaks.com/ip` |
| IP 归属 / 干净度（欺诈评分） | `https://ip123.in/` |
| 浏览器指纹（FP ID / fuzzy hash） | `https://abrahamjuliot.github.io/creepjs/` |

**可达性实测**（2026-11-20，经本机 mihomo `:21080`）：三个地址均返回 **200**。

**标签行为实测**：`node scripts/tabs-check.py` **13 条断言全过** ——
启动开检测页 → 停止时记住标签 → 再启动恢复**且不重复**（连做两轮都不重复）。

检测页列表用 **`ZW_DETECT_URLS`** 覆盖，**逗号分隔**：

```bash
ZW_DETECT_URLS="https://browserleaks.com/ip,https://ip123.in/"
```

两个开关要分清（这里的语义很容易搞错，我第一版文档就写错了）：

| 想做什么 | 怎么设 |
|---|---|
| 换掉检测页 | `ZW_DETECT_URLS="url1,url2"`（留空 = **仍用默认那三个**） |
| **一个都不打开** | `ZW_OPEN_DETECT_ON_START=false`（默认 `true`） |

> 更正（2026-11-20）：这段原先写的是 `ZW_CHECK_PAGES` / 换行分隔 / "设为空则不打开" ——
> **三处都错**。代码读的是 `ZW_DETECT_URLS`、按逗号切分、**留空回落默认三个**；
> 要关掉得用 `ZW_OPEN_DETECT_ON_START=false`。
> 照旧文档设环境变量会静默不生效 —— 这类错误比崩溃更难发现。


## 附：为什么带凭据的代理要走本机中继（实测结论）

用户问过：「**如果 Chrome 支持不好的话，你可以再单独创建一个 Firefox 类型的**」。
这是个条件句，判断依据是 Chrome 到底支持到什么程度。下面是实测结果。

### 实测（2026-11-20，ungoogled-chromium 150 / Chrome 157）

| 给 Chrome 的 `--proxy-server` | 代理端收到什么 |
|---|---|
| `socks5://user:pass@host:port` | **什么都没收到**（握手记录为空） |
| `socks5://host:port`（无凭据） | 正常握手 |
| `http://127.0.0.1:<中继端口>`（无凭据，走中继） | 正常，且**上游收到带凭据的握手** |

结论：**Chromium 从不解析 proxy URL 里的 userinfo**，`u:p@` 会被直接丢弃 ——
所以带凭据的代理如果直接写进 `--proxy-server`，代理根本没被连上，
页面其实是直连出去的。这比"认证失败"更危险：**看起来能用，实际在裸奔**。

### 所以产品怎么做

带凭据的代理 **一律走本机中继**（`services/proxyrelay.py`）：

```
Chrome  ──无凭据──►  127.0.0.1:<中继端口>  ──带凭据──►  上游代理  ──►  目标
         http://                       socks5/http + auth
```

中继替 Chrome 补 `Proxy-Authorization: Basic …`（HTTP）或 RFC 1929 握手（socks5）。
真机记录（经中继访问 example.com）：

```
VER=5 METHODS=[0, 2]
  AUTH user=b'cf1b481103' pass=b'51ec63a321'
  CONNECT example.com:443
```

### 还需要 Firefox 吗

**不需要单独的 Firefox 引擎**。凭据问题已经由中继解决，Chrome/Chromium 系
在"带认证代理"这个场景下是可用的。`ZW_ENGINE_POLICY` 里也没有 Firefox 分支，
加一个只会多一套打包/升级/指纹兼容的负担，不解决任何现有问题。

> 补充：HTTP 代理的 CONNECT 隧道同样验证过（`200 Connection Established` +
> 隧道内数据正常），见 `tests/test_proxyrelay_http_e2e.py`。
