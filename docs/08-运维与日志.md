# 08 · 运维与日志

---

## 一、日志在哪

| 日志 | 路径 | 内容 |
|---|---|---|
| **全局日志** | `<数据根>/logs/zhiwen.log` | 所有模块的 JSON 行，按天滚动，保留 `ZW_LOG_KEEP_DAYS` 天（默认 14） |
| **环境事件** | `<数据根>/profiles/<环境id>/profile.log` | 该环境的启停、同步、指纹重置等事件 |
| **浏览器输出** | `<数据根>/profiles/<环境id>/browser.log` | Chromium 自己的 stdout/stderr（排"起来就退"必看） |
| **hub 日志** | 容器内 `/data/logs/hub.log` | `docker logs zw-hub` 也能看 |
| **审计** | SQLite 表 `audit_log`，通过 `/api/v1/audit` 查 | 谁在什么时候动了什么 |

`<数据根>` 默认：
- Windows：`%LOCALAPPDATA%\zhiwen`
- Linux：`~/.local/share/zhiwen`

## 二、日志长什么样

**控制台**（人类可读，`ZW_LOG_JSON=false` 时）：

```
2026-11-16 04:05:12 INFO  [zw.lifecycle] 启动环境 name=demo-01 port=21001
2026-11-16 04:05:15 INFO  [zw.lifecycle] 环境已就绪 name=demo-01 pid=48231 ws=ws://127.0.0.1:21001/devtools/browser/…
2026-11-16 04:06:02 INFO  [zw.sync]      推送成功 name=demo-01 rev=3 size=5626 cookies=1
```

**文件**（永远是 JSON 行，方便机器处理）：

```json
{"ts":"2026-11-16T04:05:12","level":"INFO","logger":"zw.lifecycle","msg":"启动环境","profile_name":"demo-01","profile_id":"4c1f…"}
{"ts":"2026-11-16T04:06:02","level":"INFO","logger":"zw.sync","msg":"推送成功 name=demo-01 rev=3 size=5626 cookies=1"}
```

### 常用查询

```bash
LOG=<数据根>/logs/zhiwen.log

# 所有错误
jq -c 'select(.level=="ERROR")' "$LOG" | tail -20

# 某个环境的完整轨迹
jq -c 'select(.profile_name=="demo-01")' "$LOG"

# 最近一小时的同步动作
jq -c 'select(.logger=="zw.sync")' "$LOG" | tail -30

# 谁在连 CDP
jq -c 'select(.logger=="zw.gateway")' "$LOG" | tail -30
```

## 三、审计表

```bash
curl -s -H "Authorization: Bearer $T" \
  "http://127.0.0.1:8730/api/v1/audit?limit=20" | jq -r '.data.items[] | "\(.ts|todate) \(.action) \(.profile_id) \(.result)"'
```

记录的 8 类事件：

`profile.create` `profile.update` `profile.delete` `profile.start` `profile.stop`
`profile.fingerprint_reset` `profile.unlock`
`cookie.read` `cookie.write` `storage.write`
`sync.push` `sync.pull`
`extension.install`
`cdp.connect` `cdp.disconnect`

`detail` 字段是 JSON，**不含任何 cookie 内容或密码**（只记条数与指纹）。

## 四、日常运维

### 每天/每次开机

```bash
zw doctor          # 自检
zw stats           # 看一眼容量
```

### 每周

```bash
# 清理已停止环境的缓存（会释放大量磁盘，不影响登录态）
curl -X POST -H "Authorization: Bearer $T" http://127.0.0.1:8730/api/v1/maintenance/trim

# 清 staging 残留 + 过期令牌
curl -X POST -H "Authorization: Bearer $T" http://127.0.0.1:8730/api/v1/maintenance/cleanup
```

### 每月

- 看 `zw audit` 有没有异常（大量 `auth.fail`、`lease.takeover`）
- 检查 `<数据根>/profiles` 的磁盘占用
- 备份 SQLite：`sqlite3 zhiwen.db ".backup zhiwen-$(date +%F).db"`
- 看一眼内核是否有新版本（[fingerprint-chromium releases](https://github.com/adryfish/fingerprint-chromium/releases)）

### 备份清单

| 要备份 | 大小 | 说明 |
|---|---|---|
| `zhiwen.db` | 百 KB | 环境元数据。丢了可以从环境目录部分恢复 |
| `profiles/` | 几十 MB–几十 GB | 真正的数据 |
| `<hub>/data/` | 视版本数 | 加密快照。丢了本地还有 |
| **主密码** | 零字节 | 存在你脑子里/密码管理器里，**这是唯一不能丢的东西** |

## 五、容量与清理

```bash
zw stats
# 关注 disk_bytes / disk_human
```

清理策略（按收益从高到低）：

1. **trim 已停止环境的缓存** —— 通常能回收 80%+ 的空间
2. **删掉不用的环境**：`zw profile rm <名字> --purge`
3. **清理旧的 `udd.bak.*`**：pull 会自动只留 2 份，但异常中断可能留下更多

## 六、开机自启

### Windows

用「任务计划程序」：

```powershell
$action = New-ScheduledTaskAction -Execute "C:\path\zhiwen_brwo\.venv\Scripts\pythonw.exe" `
  -Argument "-m zw_core.main" -WorkingDirectory "C:\path\zhiwen_brwo"
$trigger = New-ScheduledTaskTrigger -AtLogOn
Register-ScheduledTask -TaskName "知纹核心" -Action $action -Trigger $trigger -RunLevel Highest
```

或者用 `nssm` 注册成服务（更稳，开机即启，不需要登录）：

```powershell
nssm install ZhiwenCore "C:\path\zhiwen_brwo\.venv\Scripts\python.exe" "-m zw_core.main"
nssm set ZhiwenCore AppDirectory "C:\path\zhiwen_brwo"
nssm set ZhiwenCore AppEnvironmentExtra ZW_ADMIN_TOKEN=xxx ZW_HUB_URL=http://192.168.3.5:8700
nssm start ZhiwenCore
```

见 [部署指南](03-部署指南.md) §3.2 的 systemd 单元。

### hub（3.5）

已经配了 `restart: unless-stopped`，Docker 起来就自动起。

## 九、两个容易踩的"自己挡自己"

### 9.1 残留租约

以前有个真实缺陷：租约的 owner 是**每个实例随机生成**的，于是 `stop` 里新建一个实例去释放时
"owner 对不上"，文件永远删不掉 —— 下次 `start` 会被自己的旧租约挡住 90 秒，报 `PROFILE_BUSY`。

现在：

- owner 改成**进程级稳定**（`主机名:pid:随机8位`），同一进程内所有实例共享；
- `stop` / `unlock` 用 `force_release()`，无条件删；
- **启动时会自动清理"持有者进程已死"的租约**，日志里会写 `清理死租约 ['xxx']`。

### 9.2 CDP 令牌悄悄堆积

`GET /profiles/{id}` 这种会被 UI 反复调用的接口**不签发令牌**（只返回 `cdp_ready` 与提示）。
真正签发只有两个入口：`POST /profiles/{id}/start` 和 `GET /profiles/{id}/cdp`。

即便如此，还是加了两道保险：

- 每个环境最多保留 20 个有效令牌，超出按时间裁掉最老的；
- 健康巡检每轮清一次全库过期令牌，日志里写 `清理过期 CDP 令牌 N 个`。

`zw stats` 里能看到 `cdp_tokens: {total, live, expired}`，如果 live 一直涨就是有客户端在刷。

---

### 9.3 孤儿浏览器进程

core 被 `kill -9`、数据库被重置、手动删了环境目录 —— 这些情况下浏览器进程会留在后台，
占内存、占端口，还会让同名环境下次启动撞 `SingletonLock`。

现在的处理：

- **启动时自动清**：扫描所有以 `<数据目录>/profiles/` 下某个目录为 `--user-data-dir` 的
  **根浏览器进程**（`--type=` 的子进程不算），凡是"环境不在库里"或"环境状态不是 running"的，
  一律终止。日志里会写 `清孤儿浏览器 N 个`。
- **手动清**：`POST /api/v1/maintenance/reap-orphans`
- **绝不误杀**：环境状态是 `running` 的一律跳过 —— 这是"控制面重启不影响正在用的浏览器"的底线。

## 十、五个自检脚本

按从内到外分三层：逻辑 → 单机全能力 → 跨机 / 前端。

```bash
# 1. 单元测试（132 项，不需要浏览器，含真起 hub 子进程的同步集成测试）
.venv/bin/python -m pytest tests -q

# 2. 单机全能力（63 项，真开浏览器；服务需要先跑起来）
ZW_CORE=http://127.0.0.1:8730 \
ZW_ADMIN_TOKEN=$ZW_ADMIN_TOKEN \
ZW_SYNC_PASSWORD=$ZW_SYNC_PASSWORD \
  .venv/bin/python scripts/e2e-check.py
```

第 2 个的特点是**每项都有"跳过"这个第三态**：它不会把"这台机器没有 GPU"报成失败，
而是打出 `⚠️ 跳过 — 原因`，最后单独列出跳过项。所以它既能当验收，也能当"这台机器能干什么"的体检。

```bash
# 3. 跨机端到端（30 项，两台真机器 + 一台 hub）
ZW_A=http://192.168.3.6:8730 ZW_TA=xxx \
ZW_B=http://192.168.3.5:8731 ZW_TB=xxx \
ZW_SYNC_PASSWORD=xxx \
  .venv/bin/python scripts/e2e-cross-machine.py

# 4. 网关接管（20 项，Playwright 通过网关连浏览器）
ZW_CORE=http://127.0.0.1:8730 ZW_ADMIN_TOKEN=xxx \
  node scripts/gateway-check.cjs

# 5. 控制台交互（16 项，逐视图点一遍 + 启停 + 表单 + 深浅色）
ZW_CORE=http://127.0.0.1:8730 ZW_ADMIN_TOKEN=xxx \
ZW_CHROME=/path/to/chrome node scripts/ui-check.cjs
```

第 5 个特别值得留：它能抓出"接口都好但前端点不动"这类问题。
0.1.0 里的租约泄漏缺陷、0.2.0 里"同步徽章把未同步显示成同步一致"的误报，都是它先暴露的。
它还会把每个视图截图到 `/tmp/zhiwen-ui-*.png`（可用 `ZW_SHOT_DIR` 改），出问题时直接看图。

```bash
# 额外：孤儿进程检查（只扫描不杀）
curl -s -X POST -H "Authorization: Bearer $T" \
  http://127.0.0.1:8730/api/v1/maintenance/reap-orphans | jq
```

`scanned` 是扫到的根浏览器进程数，`orphans` 里会写清每个的理由。

> 注意：`reap-orphans` **会真的杀进程**。它会跳过 `running` 的环境，但如果你手动改过数据库状态，
> 请先看返回里的 `details[].reason` 再决定。

## 十一、空闲回收与崩溃退避

这两条是 0.2.0 新增的，默认都不介入，需要时用环境变量打开。

### 空闲回收

```
ZW_IDLE_TIMEOUT=1800     # 30 分钟没人用就停掉
```

"没人用"的判据是 `last_active_at`（最后一次被访问的时间）加上**当前是否有活的 CDP 连接**——
只要有客户端连着（Playwright 正在跑），无论多久都不会被回收。这是刻意的：
自动化跑长任务的场景下被回收一次就前功尽弃。

不设 `ZW_IDLE_TIMEOUT`（默认 0）就永远不回收。

### 崩溃退避

```
ZW_RESTART_MAX_ATTEMPTS=3    # 连续失败 3 次就不再试
ZW_RESTART_BACKOFF=5         # 退避基数（秒），按次数线性放大，上限 30 秒
```

0.1.0 没有上限：一个坏内核会让程序无限重启浏览器，把 CPU 打满。
现在达到上限后环境停在 `crashed` 状态并在 `last_error` 里写清原因，
同时在审计里记一条 —— 需要人来看，而不是继续无意义地重试。

手动 `zw profile start` 会把 `restart_count` 清零，等于"我修好了，再试一次"。
